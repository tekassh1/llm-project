# Отчёт по проекту «Ассистент сервисной службы на Graph RAG»

Репозиторий: https://github.com/tekassh1/llm-project.git

## 1. Задача

Компания «ПолярТех» делает и обслуживает холодильное оборудование: витрины «Арктика», моноблоки «Бриз» и чиллеры «Гольфстрим». Если витрина в магазине stops, товар портится, поэтому в договорах прописано время восстановления и штрафы за его нарушение. Диспетчер принимает заявку, ему называют модель и код ошибки с панели. Чтобы отправить инженера с нужной деталью, диспетчер должен выяснить пять вещей:

1. какой узел отказал
2. какая деталь стоит на этом месте в этой модели
3. не снята ли деталь с производства и чем заменена
4. есть ли она на ближайшем складе
5. сколько она стоит

Первые три ответа ищутся по документам (руководствам, бюллетеням, регламентам, отчётам инженеров). Остатки и цены берутся только из ERP, они меняются каждый день. Сейчас диспетчер ищет деталь в среднем 12 минут, и в каждой двенадцатой заявке заказывается деталь, которая уже снята с производства. ERP отклоняет такой заказ, и поиск приходится начинать заново.

Пример, где плоский RAG ошибается: «Какую деталь заказать при ошибке E-17 на AR-210?»

Ответ складывается из трёх фактов из разных документов:
1. E-17 - отказ пускового реле (руководство по модели).
2. В AR-210 пусковое реле - это деталь P-1042 (руководство по модели).
3. P-1042 снята с производства, заменена на P-1042B (сервисный бюллетень).

Плоский RAG ищет чанки, похожие на вопрос по смыслу. Руководство и отчёты ближе к тексту вопроса, чем бюллетень, поэтому модель видит только P-1042 и советует заказать старую деталь. ERP отклоняет заказ. В графе знаний эти же факты связаны цепочкой: ошибка E-17 указывает на реле, реле в модели AR-210 - деталь P-1042, а P-1042 заменена на P-1042B. Graph RAG проходит по этой цепочке и выдаёт правильный ответ - P-1042B.

## 2. Решение

Система работает в два этапа: сначала один раз собирается индекс, затем на каждый вопрос даётся ответ.

### 2.1 Извлечение (extraction.py, FR-1)

Документы режутся на 92 чанка. Каждый чанк начинается с заголовка документа, поэтому модель понимает, о какой модели речь. Для каждого чанка языковая модель вызывается с JSON-схемой EXTRACTION_SCHEMA: в запросе описаны типы сущностей, направление связей и пример ответа. Модель возвращает сущности и связи в формате JSON.

После этого код проводит фильтрацию:
- имена приводятся к каноническому виду (коды AR-210, P-1042B; названия из словаря);
- код принимается только если он есть в тексте чанка (чтобы модель не выдумала что-то вроде SP-1-04);
- связь остаётся, если оба её конца найдены и типы концов соответствуют схеме RELATION_SIGNATURES;
- если ответ модели не разбирается по схеме, делается одна повторная попытка, после второй неудачи возвращается пустой результат;
- число отброшенных сущностей и связей записывается в поле dropped.

Фильтрация делается кодом, а не только моделью. Маленькая модель (Qwen3 4B) часто путает направление связи или выдумывает имена. Код отсекает такие ошибки до того, как они попадут в граф.

### 2.2 Граф (graph_builder.py, FR-2)

Все тройки из всех чанков объединяются в один направленный граф networkx.DiGraph:
- узел: идентификатор Part:P-1042, атрибуты type, name, sources;
- ребро: атрибуты type, weight (сколько разных чанков встретили эту связь) и sources;
- попадают только связи, соответствующие схеме (Relation.matches_schema());
- если две детали связаны REPLACED_BY в обе стороны, остаётся связь с большим весом, при равных весах обе удаляются; число таких конфликтов записывается в graph.graph["conflicts"].

Вес ребра - число чанков, а не просто 1. Это позволяет различать отказ узла, который зафиксирован в восьми отчётах, и отказ из одного отчёта, и использовать веса при обзорных вопросах.

### 2.3 Сообщества (communities.py, FR-3)

Граф разбивается на сообщества алгоритмом Лувена (networkx.louvain_communities) с фиксированным seed, чтобы результат был воспроизводимым. Каждый узел попадает ровно в одно сообщество, номера сообществ идут с нуля. Для каждого сообщества модель одним вызовом пишет сводку длиной до 150 слов. Числа для сводки (какие сущности входят, какие связи частые) считает код по весам рёбер и передаёт модели готовыми.

Числа считаются кодом, модель только формулирует текст. Это исключает выдуманные статистики в сводках.

### 2.4 Два режима поиска (search.py, FR-4, FR-5)

Режим local - для вопросов о конкретных сущностях:
- опорные сущности ищутся по кодам (find_codes) и названиям (find_names);
- при двух и более опорных сущностях берутся факты на путях длиной до трёх связей между ними (направление игнорируется), плюс цепочки REPLACED_BY;
- при одной опорной сущности берётся её окрестность глубиной до двух связей;
- модель получает пронумерованный список фактов (до 8000 символов) и отвечает по ним; если в фактах есть замена, отвечает последней деталью цепочки;
- если код из вопроса отсутствует в графе или фактов не нашлось, возвращается refused=True без вызова модели.

Режим global - для обзорных вопросов (схема map-reduce):
- шаг map: вопрос задаётся каждой сводке сообщества, модель возвращает JSON {"answer": "...", "score": N};
- шаг reduce: частичные ответы с оценкой выше 0 объединяются одним вызовом модели;
- если подходящих ответов нет, возвращается refused=True.

Local ищет пути между сущностями, а не просто соседей. Это отличие от плоского RAG - вопрос «E-17 на AR-210» разрешается через общий узел «пусковое реле», который соединяет две разные модели.

### 2.5 Агент (agent.py, tools.py, FR-6 – FR-10)

Пять инструментов (function calling):
1. search_knowledge - поиск по графу (режим local);
2. summarize_topic - обзорный поиск по сводкам (режим global);
3. check_stock(part_id, warehouse) - остаток на складе и признак discontinued;
4. get_price(part_id) - цена в рублях и признак discontinued;
5. create_service_order(part_id, warehouse, qty, model) - создание заказа.

Цикл агента (ReAct): рассуждение, вызов инструмента, наблюдение, до max_steps=6 шагов. Проверки:
- склад только из фиксированного списка (Москва, Санкт-Петербург, Казань, Новосибирск);
- номер детали вида P-1042 или P-1042B, и он должен встречаться в вопросе или в результатах предыдущих инструментов;
- количество в заказе должно быть названо пользователем;
- при ErpUnavailable повтор до 3 раз;
- заказ создаётся только при confirm=True, иначе возвращается needs_confirmation=True и pending_action;
- перед выдачей ответа коды, цены и остатки сверяются с вопросом и результатами инструментов (FR-10); при расхождении один раз просит модель исправить, после второго - отказ.

## 4. Где граф помогает и где уступает

### Пример 1. Граф выигрывает - многошаговый вопрос

Вопрос: «Какую деталь заказать при ошибке E-17 на AR-210?»

Плоский RAG выбирает руководство и отчёты, видит только P-1042 и рекомендует старую деталь. ERP отклоняет заказ.

Graph RAG проходит по цепочке: ошибка E-17 означает отказ пускового реле, реле в модели AR-210 - деталь P-1042, P-1042 заменена на P-1042B. Выдаётся правильная деталь P-1042B с источником bulletin_SB-2025-03.md.

### Пример 2. Граф уступает - обзорный вопрос

Вопрос: «Какой узел чаще всего отказывает в линейке «Арктика»?»

Эталонный ответ - «пусковое реле», но в поле evidence вопроса пусто, а source_groups - пустой список. Режим global отвечает по сводкам сообществ, но если сообщества не совпадают с линейками (алгоритм Лувена разбил узлы иначе), модель может не найти достаточно доказательств. Плоский RAG на этом вопросе тоже ошибётся, но глобальный поиск по сводкам может дать неполный ответ, если веса рёбер внутри сообщества не отражают реальную частоту отказов.

## 5. Ошибки системы

| # | Ошибка | Этап | Описание |
|---|---|---|---|
| 1 | Модель возвращает связь с перевёрнутым направлением (новая деталь «заменена» старой) | Извлечение (FR-1) | Проверка по схеме пропускает, так как типы концов верны. Обнаруживается при сборке графа при сравнении весов встречных рёбер (FR-2). |
| 2 | Код из вопроса отсутствует в графе (например, E-99 или AR-999) | Поиск (FR-4) | local_search возвращает refused=True без вызова модели - корректный отказ, но пользователь не получает ответа. |
| 3 | Модель называет склад вне списка или подставляет количество, не названное пользователем | Агент (FR-6, FR-7) | Код проверки аргументов отклоняет вызов и возвращает ошибку модели; цикл продолжается, но тратит шаги. |
| 4 | ERP недоступна (ErpUnavailable) | Инструмент ERP (FR-8) | Вызов повторяется до 3 раз; после третьей неудачи шаг записывается с ошибкой, а ответ сообщает, что данные получить не удалось. |
| 5 | Модель выдумывает код детали вне корпуса | Генерация (FR-10) | Финальная проверка _answer_is_grounded сверяет коды в ответе с вопросом и результатами инструментов; при несовпадении один раз просит исправить, после второго - отказ. |

## 6. Границы системы

Ассистент передаёт на подтверждение человека только создание заказа детали (create_service_order). Это обеспечено так:

- При confirm=False (по умолчанию) агент останавливается перед вызовом create_service_order и возвращает needs_confirmation=True и pending_action с параметрами заказа.
- Заказ создаётся только при confirm=True, и его номер попадает в итоговый ответ (FR-9).
- Количество для заказа должно быть названо пользователем в вопросе; иначе агент возвращает уточняющий вопрос (FR-7).
- Все остальные действия (поиск по документам, проверка остатка, цена) выполняются автоматически без подтверждения.

## 7. Следующий шаг

Идея: добавить гибридный поиск - комбинировать поиск по графам с векторным поиском по чанкам (как в плоском RAG) для случаев, когда опорная сущность не найдена в графе, но relevant текст есть в документах. Проверить на 24 открытых вопросах: доля верных ответов должна вырасти, в частности на вопросах типа local, где сейчас возможен отказ из-за отсутствия кода в графе. Метрика для проверки: accuracy по всем 24 вопросам до и после изменения.
